**术语（首次）**：  
- **数据库（Database）**：有组织地存放多张表的「数据仓库小房间」。  
- **表（Table）**：像Excel工作表，一行一件事，一列一个属性。  
- **字段（Column/Field）**：表的一列，如 `priority`（优先级）。  
- **行（Row/Record）**：表的一条记录，如一张工单。  
- **主键（Primary Key）**：能唯一标识一行的字段，如 `ticket_id`。  
- **外键（Foreign Key）**：指向另一张表主键的字段，用来「关联」，如工单上的 `customer_id`。

## 知识点卡片 KP-M01-01

- **知识点ID**：`KP-M01-01`
- **知识点名称**：用Excel思维理解数据库、表、字段、行
- **所属模块**：`M01`
- **前置知识**：`KP-M00-02`
- **学习目标（1—2条，可验证）**：
  1. 能指着样本CSV说出：哪些是字段名、哪一行是一条工单。
  2. 能解释「数据库里可以有多张表」像「一个Excel文件里多个工作表」。
- **零基础解释（不超过200字）**：  
  你熟悉的Excel：表头=字段名，每一行=一条业务对象。数据库几乎一样，但更强调类型规矩、唯一编号、多表关联，并且用SQL语言查询，而不是只靠筛选按钮。先把「表=结构化清单」建立起来，后面学SQL就不会飘。
- **生活类比**：  
  快递站点的纸质登记本：每一横行是一个包裹；本子顶部印着「单号、收件人、电话」——那就是字段。
- **具体示例**：  
  打开 `tickets_sample.csv`：第一行 `ticket_id,customer_id,...` 是字段；`T1001,...` 是一行工单。
- **操作步骤/代码/命令（逐行注释）**：

```text
步骤1：用Excel/WPS/VS Code打开 assets/samples/tickets_sample.csv
步骤2：数一数有多少个字段（列），写下来
步骤3：数一数有多少行业务数据（不含表头），写下来
步骤4：任选一行，用中文口述：「这是客户Cxx的一张yy类工单，优先级zz」
```

- **学习案例对应（本课默认：客服工单；可替换为订单/线索/审批等）**：  
  座席系统里的「工单列表页」背后通常就是一张（或几张）工单表。
- **练习任务（可在20分钟内完成）**：  
  画出 `tickets` 表的「字段清单」，每个字段用一句话写业务含义（可抄样本，但必须自己写含义）。
- **自测题（2—3题，附答案）**：
  1. `subject` 是字段还是行？ → **字段（列）**。
  2. 一行工单是否应包含两个不同的 `ticket_id`？ → **否**，一行一个工单编号。
  3. 数据库可以只有一张表吗？ → **可以**，但真实业务通常多张表。
- **常见错误与排查**：
  - 错误：把整张CSV叫作「一个字段」。排查：字段是列。
  - 错误：把表头也算进业务行数。排查：第一行是字段名。
- **复用标签**：`#SQL` `#数据基础` `#零基础` `#可复用`
- **建议时长**：25 分钟
- **掌握标准**：能独立指认样本中的字段与行，并口述一行业务含义。

## 知识点卡片 KP-M01-02

- **知识点ID**：`KP-M01-02`
- **知识点名称**：主键：为什么每张工单需要唯一编号
- **所属模块**：`M01`
- **前置知识**：`KP-M01-01`
- **学习目标（1—2条，可验证）**：
  1. 能定义主键：唯一标识一行的字段。
  2. 能判断「客户姓名」为何不适合做工单主键。
- **零基础解释（不超过200字）**：  
  主键是表格的「身份证号」。有了它，系统才知道你说的是哪一张工单，不会把两张「都叫退款」的单子搞混。主键必须唯一，且一般不轻易改。
- **生活类比**：  
  医院用病历号，不用「叫张伟的那位」——重名太多。
- **具体示例**：  
  `ticket_id=T1016` 唯一指向「电池鼓包」那张单；即使还有别的质量问题单，也不会冲突。
- **操作步骤/代码/命令（逐行注释）**：

```sql
-- 以下在 SQLite 中运行（先执行 tickets_sample.sql 建库）
-- 业务含义：查看所有工单编号，确认没有重复

SELECT ticket_id   -- 只取主键这一列
FROM tickets;      -- 来源：工单表

-- 检查是否有重复主键（结果应为空）
SELECT ticket_id, COUNT(*) AS cnt  -- 计数每个编号出现几次
FROM tickets
GROUP BY ticket_id                 -- 按编号分组（第2周会详解，这里先当检查工具）
HAVING COUNT(*) > 1;               -- 只显示出现超过1次的（应无结果）
```

- **学习案例对应（本课默认：客服工单；可替换为订单/线索/审批等）**：  
  客服说「帮我看一下T1018」——主键让检索、改派、质检评论都钉在同一张单上。
- **练习任务（可在20分钟内完成）**：  
  假设去掉 `ticket_id`，只用 `subject` 当主键，写出可能发生的2个业务事故。
- **自测题（2—3题，附答案）**：
  1. 主键可否为空？ → **一般不可以**（必须能标识到具体一行）。
  2. 两行能否共享同一主键？ → **不能**。
  3. `status` 适合当主键吗？ → **不适合**，大量工单状态相同。
- **常见错误与排查**：
  - 错误：认为「看着像唯一」就可以。排查：用COUNT检查，并用规则保证写入唯一。
- **复用标签**：`#SQL` `#主键` `#数据质量` `#可复用`
- **建议时长**：25 分钟
- **掌握标准**：能解释主键，并能举出1个「不能当主键」的字段及理由。

## 知识点卡片 KP-M01-03

- **知识点ID**：`KP-M01-03`
- **知识点名称**：外键：工单如何「挂靠」到客户
- **所属模块**：`M01`
- **前置知识**：`KP-M01-02`
- **学习目标（1—2条，可验证）**：
  1. 能说明外键是「指向另一表主键的字段」。
  2. 能在样本中指出 `tickets.customer_id` 对应 `customers.customer_id`。
- **零基础解释（不超过200字）**：  
  外键像快递单上的「会员号」：工单表不需要把客户姓名、城市整份抄一遍，只存客户编号；详细资料放在客户表。要拼在一起看时，用编号对齐（这就是之后JOIN要做的事）。
- **生活类比**：  
  学生证号印在借书卡上：借书卡不写家庭住址全文，要用证号去学生档案查。
- **具体示例**：  
  工单 `T1001` 的 `customer_id=C01` → 客户表里 C01 是张敏、上海。于是可知「上海客户张敏的物流延误单」。
- **操作步骤/代码/命令（逐行注释）**：

```sql
-- 查看工单上的客户编号（外键）
SELECT ticket_id, customer_id, subject  -- 工单号、外键、标题
FROM tickets
LIMIT 5;                                -- 先看5行，避免刷屏

-- 查看客户表主键
SELECT customer_id, customer_name, city
FROM customers
WHERE customer_id = 'C01';              -- 找出外键指向的那一位客户
```

- **学习案例对应（本课默认：客服工单；可替换为订单/线索/审批等）**：  
  白金客户升级工单：先凭外键找到客户等级，再决定是否走绿色通道（第2周JOIN后可一次查出）。
- **练习任务（可在20分钟内完成）**：  
  手写一张「关系小图」：方框customers、方框tickets，箭头从 `tickets.customer_id` 指向 `customers.customer_id`，并标注「外键→主键」。
- **自测题（2—3题，附答案）**：
  1. 外键一定在「多」的那一侧表吗？ → **常见是**（一张客户多张工单时，外键在工单表）。
  2. 没有外键能否存客户名在工单表？ → **能**，但易不一致、难维护。
  3. `customer_id` 在customers表是什么键？在tickets表呢？ → **主键；外键**。
- **常见错误与排查**：
  - 错误：把外键理解成「密码」。排查：它是关联指针，不是安全认证。
  - 错误：工单里写了不存在的客户编号。排查：这叫「孤儿数据」，建外键约束可防止。
- **复用标签**：`#SQL` `#外键` `#数据建模` `#可复用`
- **建议时长**：25 分钟
- **掌握标准**：能画外键关系图，并能解释为何不把客户所有字段塞进工单表。

## 知识点卡片 KP-M01-04

- **知识点ID**：`KP-M01-04`
- **知识点名称**：读懂工单样本字典（为取数做准备）
- **所属模块**：`M01`
- **前置知识**：`KP-M01-03`
- **学习目标（1—2条，可验证）**：
  1. 能不看文档口述至少6个 `tickets` 字段的业务含义。
  2. 能根据字段选出「找高优先级未解决单」需要用到的列。
- **零基础解释（不超过200字）**：  
  数据字典=字段说明书。FDE取数前先对齐字段含义，否则SQL写对了也可能取错业务。本默认案例中要分清 `category`（类型）、`priority`（紧急程度）、`status`（进度）；换到订单案例如对应品类/金额档/履约状态。
- **生活类比**：  
  医院化验单上的缩写表：不懂缩写就会误读「高」是好事还是坏事。
- **具体示例（tickets字段字典）**：

| 字段 | 含义 | 示例值 |
| --- | --- | --- |
| ticket_id | 工单主键 | T1010 |
| customer_id | 客户外键 | C04 |
| created_at | 创建时间 | 2026-10-05 09:25:00 |
| channel | 进线渠道 | hotline |
| category | 问题分类 | 物流 |
| priority | 优先级 | 高 |
| status | 状态 | 处理中 |
| subject | 标题 | 生鲜变质 |
| content | 正文 | 冷链超时… |

- **操作步骤/代码/命令（逐行注释）**：

```sql
-- 预览全部字段的前3行，建立「数据感觉」
SELECT *
FROM tickets
LIMIT 3;

-- 只看分类、优先级、状态（后续筛选常用）
SELECT ticket_id, category, priority, status, subject
FROM tickets;
```

- **学习案例对应（本课默认：客服工单；可替换为订单/线索/审批等）**：  
  晨会要「高优先级且未解决」：字段上就是 `priority='高'` 且 `status` 不在已解决/已关闭。
- **练习任务（可在20分钟内完成）**：  
  填写：若要统计「微信渠道的退款单」，需要哪些字段？写出过滤条件中文版（还不用SQL也行）。
- **自测题（2—3题，附答案）**：
  1. `channel` 与 `category` 区别？ → **渠道 vs 问题类型**。
  2. 「升级」是优先级还是状态？ → **在本样本中是 status（状态）**。
  3. 找电池安全隐患相关单，优先看哪些字段？ → **subject/content，辅以category=质量、priority**。
- **常见错误与排查**：
  - 错误：用 `category` 当紧急程度。排查：紧急程度看 `priority`。
- **复用标签**：`#SQL` `#数据字典` `#案例-工单` `#可复用`
- **建议时长**：25 分钟
- **掌握标准**：能默写核心字段含义，并能用中文写出1个筛选需求对应的字段条件。
