# 模块 M03｜筛选排序与结果可读（WHERE / ORDER BY / LIMIT）

| 复用标签 | `#SQL` `#WHERE` `#ORDERBY` `#LIMIT` `#可复用` |

**术语（首次）**：  
- **WHERE**：筛选条件，「只要满足……的行」。  
- **ORDER BY**：排序，「按某字段从高到低/从早到晚排列」。  
- **LIMIT**：限制返回行数，「只要前N条」。  
- **运算符**：比较符号，如 `=`（等于）、`<>`或`!=`（不等于）、`>` `<` 等。  
- **AND / OR**：同时满足 / 满足其一。  
- **LIKE**：模糊匹配（例如标题里包含「退款」）。

## 知识点卡片 KP-M03-01

- **知识点ID**：`KP-M03-01`
- **知识点名称**：WHERE等值筛选：只要高优先级
- **所属模块**：`M03`
- **前置知识**：`KP-M02-01`
- **学习目标（1—2条，可验证）**：
  1. 能写出 `priority = '高'` 的筛选查询。
  2. 能解释：字符串值一般要用引号包起来。
- **零基础解释（不超过200字）**：  
  WHERE跟在FROM后面，用来丢掉你不关心的行。等值筛选最常见：某字段等于某个值。注意：`'高'` 是文本，要加引号；若是纯数字字段，有的库可不加引号，但初学统一养成「文本加引号」习惯。
- **生活类比**：  
  从一叠快递里只抽「写着易碎」的——其他先放回。
- **具体示例**：晨会先看所有高优先级工单。
- **操作步骤/代码/命令（逐行注释）**：

```sql
SELECT
  ticket_id,          -- 便于会后跟进
  priority,           -- 确认确实是「高」
  status,
  subject
FROM tickets          -- 来源：工单表
WHERE priority = '高'; -- 只要优先级等于高的行；文本加单引号
```

- **学习案例对应（本课默认：客服工单；可替换为订单/线索/审批等）**：  
  值班长进系统先筛高优，避免被低优咨询淹没。
- **练习任务（可在20分钟内完成）**：  
  分别查出 `status = '升级'` 与 `channel = 'hotline'` 的工单清单。
- **自测题（2—3题，附答案）**：
  1. `WHERE priority = 高` 少了什么？ → **文本值的引号**。
  2. WHERE过滤的是列还是行？ → **行**（列仍由SELECT决定）。
  3. 筛 `category = '退款'` 属于什么筛选？ → **等值筛选**。
- **常见错误与排查**：
  - 错误：中文引号 `‘’`。排查：改英文单引号 `'`。
  - 错误：大小写或多余空格导致查不到。排查：先DISTINCT看真实值。
- **复用标签**：`#SQL` `#WHERE` `#可复用`
- **建议时长**：30 分钟
- **掌握标准**：能独立完成至少3个不同字段的等值查询并得到非空或可解释的空结果。

## 知识点卡片 KP-M03-02

- **知识点ID**：`KP-M03-02`
- **知识点名称**：AND/OR组合条件：高优且未解决
- **所属模块**：`M03`
- **前置知识**：`KP-M03-01`
- **学习目标（1—2条，可验证）**：
  1. 能用 AND 组合两个条件。
  2. 能举例说明 OR 与 AND 的业务差别。
- **零基础解释（不超过200字）**：  
  真实取数很少只有一个条件。AND表示「同时满足」；OR表示「满足其一即可」。复杂时用括号明确优先级，避免「我以为」和「数据库以为」不一致。
- **生活类比**：  
  AND：要「红色且XL」的衣服；OR：要「红色或XL」（可能拿到蓝XL）。
- **具体示例**：高优先级，且状态不是已解决/已关闭。
- **操作步骤/代码/命令（逐行注释）**：

```sql
SELECT
  ticket_id,
  priority,
  status,
  subject
FROM tickets
WHERE priority = '高'                 -- 条件1：高优
  AND status <> '已解决'              -- 条件2：不是已解决（<> 表示不等于）
  AND status <> '已关闭';             -- 条件3：也不是已关闭

-- OR 示例：升级或高优（值班加急池）
SELECT ticket_id, priority, status, subject
FROM tickets
WHERE status = '升级' OR priority = '高';
```

- **学习案例对应（本课默认：客服工单；可替换为订单/线索/审批等）**：  
  「加急池」= 高优未闭环 + 已升级工单；用AND/OR精确描述，避免口头扯皮。
- **练习任务（可在20分钟内完成）**：  
  写出：微信渠道且退款类；以及：物流类或质量类。两套SQL都运行。
- **自测题（2—3题，附答案）**：
  1. `高 AND 已解决` 与 `高 OR 已解决` 哪个结果通常更多？ → **OR通常更多**。
  2. 为什么常用括号？ → **明确运算顺序，防止误读**。
  3. `status <> '已解决' AND status <> '已关闭'` 能否写成一个IN/NOT IN？（预告） → **能**，更简洁（可自学，本周不强制）。
- **常见错误与排查**：
  - 错误：`WHERE priority = '高' OR '升级'`。排查：OR两侧都应是完整条件。
- **复用标签**：`#SQL` `#WHERE` `#逻辑条件` `#可复用`
- **建议时长**：30 分钟
- **掌握标准**：能把业务口语「高优未解决」准确翻译成AND条件并跑通。

## 知识点卡片 KP-M03-03

- **知识点ID**：`KP-M03-03`
- **知识点名称**：LIKE模糊匹配：标题/正文里搜关键词
- **所属模块**：`M03`
- **前置知识**：`KP-M03-01`
- **学习目标（1—2条，可验证）**：
  1. 能用 LIKE '%退款%' 找出标题含退款的工单。
  2. 能解释 `%` 表示「任意一段字符」。
- **零基础解释（不超过200字）**：  
  等值要求完全一样；LIKE允许「包含某段文字」。`%`是通配符：`%退款%`表示前后可有任意内容，中间出现「退款」。适合投诉文本尚未分类准、先按关键词捞人。
- **生活类比**：  
  在聊天记录搜索框输入「发票」——不必整句完全相等。
- **具体示例**：搜「鼓包」「变质」等风险词，做人工初筛。
- **操作步骤/代码/命令（逐行注释）**：

```sql
SELECT
  ticket_id,
  subject,
  content
FROM tickets
WHERE subject LIKE '%退款%'    -- 标题中包含「退款」
   OR content LIKE '%退款%';   -- 或正文包含「退款」

-- 安全风险词示例
SELECT ticket_id, subject, content
FROM tickets
WHERE content LIKE '%鼓包%' OR content LIKE '%变质%';
```

- **学习案例对应（本课默认：客服工单；可替换为订单/线索/审批等）**：  
  VOC风险初筛：先用关键词捞出可疑文本，再送AI细分类（对应闭环的取数→处理前奏）。
- **练习任务（可在20分钟内完成）**：  
  找出内容含「超时」或「补偿」的工单，记录ticket_id列表。
- **自测题（2—3题，附答案）**：
  1. `LIKE '退款'` 与 `LIKE '%退款%'` 差别？ → **前者几乎要整格等于退款；后者包含即可**。
  2. `%` 是什么？ → **任意长度通配**。
  3. LIKE能替代所有分类模型吗？ → **不能**，易漏易误，只是快筛。
- **常见错误与排查**：
  - 错误：忘记两端`%`导致查不到。排查：先用等值DISTINCT确认，再用LIKE。
  - 错误：以为LIKE区分大小写规则处处相同。排查：不同数据库不同，先用样本验证。
- **复用标签**：`#SQL` `#LIKE` `#案例-工单` `#可复用`
- **建议时长**：30 分钟
- **掌握标准**：能独立用LIKE完成一次风险词捞取，并说出其局限。

## 知识点卡片 KP-M03-04

- **知识点ID**：`KP-M03-04`
- **知识点名称**：ORDER BY排序：把最要紧的放上面
- **所属模块**：`M03`
- **前置知识**：`KP-M03-01`
- **学习目标（1—2条，可验证）**：
  1. 能按 `created_at` 降序排列。
  2. 能说明 ASC升序与DESC降序。
- **零基础解释（不超过200字）**：  
  ORDER BY决定结果谁先谁后。时间降序=最新在前；文本排序按字典序（对「高/中/低」不一定符合业务紧急度，要注意）。ASC默认升序，DESC降序。
- **生活类比**：  
  邮箱默认「最新邮件在上」——就是按时间DESC。
- **具体示例**：未解决工单按创建时间从新到旧，方便先碰最近进线。
- **操作步骤/代码/命令（逐行注释）**：

```sql
SELECT
  ticket_id,
  created_at,     -- 排序依据：创建时间
  priority,
  subject
FROM tickets
WHERE status <> '已解决' AND status <> '已关闭'
ORDER BY created_at DESC;   -- 最新创建的排在最前
```

- **学习案例对应（本课默认：客服工单；可替换为订单/线索/审批等）**：  
  队列展示：通常「最老未解决」或「最新进线」二选一；ORDER BY方向由业务规则定。
- **练习任务（可在20分钟内完成）**：  
  对高优工单按 `created_at ASC`（最老优先）排序，解释你更倾向新优先还是老优先。
- **自测题（2—3题，附答案）**：
  1. DESC是什么意思？ → **降序**。
  2. 不写ORDER BY时顺序保证吗？ → **不保证**，不要依赖「看起来的顺序」。
  3. 对中文「高中低」ORDER BY一定得到业务紧急序吗？ → **不一定**。
- **常见错误与排查**：
  - 错误：把ORDER BY写在WHERE前面。排查：常见顺序 SELECT→FROM→WHERE→ORDER BY→LIMIT。
- **复用标签**：`#SQL` `#ORDERBY` `#可复用`
- **建议时长**：25 分钟
- **掌握标准**：能按时间排序输出未闭环工单清单。

## 知识点卡片 KP-M03-05

- **知识点ID**：`KP-M03-05`
- **知识点名称**：LIMIT：只要Top N，形成可执行清单
- **所属模块**：`M03`
- **前置知识**：`KP-M03-04`
- **学习目标（1—2条，可验证）**：
  1. 能写出「高优未解决 Top 5」查询。
  2. 能说明LIMIT与「分页」直觉的关系。
- **零基础解释（不超过200字）**：  
  LIMIT限制返回行数。业务早会不可能念20页：先ORDER BY再LIMIT 5，得到可执行的「先干这几单」。它也是保护：避免一次把百万行打到屏幕或塞进AI。
- **生活类比**：  
  待办清单只撕今天最重要的3张便利贴到桌面。
- **具体示例**：高优且未闭环，按时间ASC，只要5条。
- **操作步骤/代码/命令（逐行注释）**：

```sql
SELECT
  ticket_id AS 工单号,
  created_at AS 创建时间,
  priority AS 优先级,
  status AS 状态,
  subject AS 标题
FROM tickets
WHERE priority = '高'
  AND status <> '已解决'
  AND status <> '已关闭'
ORDER BY created_at ASC   -- 最老的高优先处理（示例策略）
LIMIT 5;                  -- 只要5条，形成今日Top清单
```

- **学习案例对应（本课默认：客服工单；可替换为订单/线索/审批等）**：  
  主管派工：每天先派Top清单；其余进普通队列。这也是FDE取数服务「呈现」层的典型输出。
- **练习任务（可在20分钟内完成）**：  
  制作「今日可展示产出」：一条SQL生成Top清单；截图或粘贴结果到学习日志，并写一句策略（为何ASC或DESC）。
- **自测题（2—3题，附答案）**：
  1. LIMIT写在ORDER BY前可以吗？ → **语法上常报错或不符合习惯；应先排序再限制**。
  2. LIMIT 5是否修改数据库？ → **否**，只影响返回。
  3. 为何AI调用前常用LIMIT？ → **控制成本与延迟，先小批量验证**。
- **常见错误与排查**：
  - 错误：不ORDER BY直接LIMIT，以为「随机5条有意义」。排查：无序Top没有业务含义。
- **复用标签**：`#SQL` `#LIMIT` `#最小闭环` `#可复用`
- **建议时长**：35 分钟
- **掌握标准**：能独立交付「高优未解决Top N」查询，并口头解释排序策略。
